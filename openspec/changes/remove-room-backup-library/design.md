## Context

`de.raphaelebner:roomdatabasebackup:1.0.0-beta12` is used for exactly one thing: copying the `AppDatabase` SQLite file (`task_database`, via `context.getDatabasePath("task_database")`) between app-private storage and a user-chosen location, wired to the drawer's "Backup"/"Restore" menu items in `MainActivity`. It's configured with `backupLocation(RoomBackup.BACKUP_FILE_LOCATION_CUSTOM_DIALOG)`, no encryption.

Internally (confirmed by decompiling the library's sources jar), that mode does two things before it ever shows a picker: (1) it requests `READ_MEDIA_IMAGES`/`READ_MEDIA_AUDIO`/`READ_MEDIA_VIDEO` (API 33+) or `READ_EXTERNAL_STORAGE` (API ≤32) via `ActivityResultContracts.RequestMultiplePermissions`, failing the whole operation if any permission in that batch is denied; only then does it (2) launch `ActivityResultContracts.CreateDocument("application/octet-stream")` (backup) or `ActivityResultContracts.OpenDocument()` filtered to `application/octet-stream` (restore) — the actual Storage Access Framework (SAF) picker — and copy raw bytes through a `ContentResolver` stream. Step (1) is functionally unnecessary: SAF's whole design point is that the picker runs in the system's process with its own grant, so the calling app never needs a storage/media permission to use it. The library requests the permissions anyway and gates the picker on them, which is the direct cause of the unwanted `READ_MEDIA_*`/`READ_EXTERNAL_STORAGE` entries in this app's manifest and Play Console Data Safety form.

The app's existing architecture already isolates the platform-specific backup mechanics behind two seams: `RoomBackupBuilder` (Hilt `@ActivityScoped`, built with an `@ActivityContext`, produces a `BackupModel`) and `RoomBackupHandler` (Hilt `@Singleton`, context-free, takes a `BackupModel` and exposes `suspend fun backupInLocalStorage/restoreInLocalStorage`). `MainActivity` builds one `BackupModel` eagerly in `onCreate` and reuses it for both backup and restore. This split exists because SAF-style `registerForActivityResult` launchers must be registered on a `ComponentActivity`/`Fragment` before it reaches `STARTED`, while the actual backup/restore call can happen later, from a `ViewModel` coroutine, without an Activity reference. `AppDatabase` is a process-wide singleton (`AppDatabase.invoke(context)` with a `@Volatile instance`); after either backup or restore closes and swaps the underlying file, `MainViewModel` already sets `needsRestartApp = true`, and `MainActivity` restarts the app — this is how the current library papers over the stale-singleton-after-close problem, and nothing here needs to change that.

## Goals / Non-Goals

**Goals:**
- Remove the `de.raphaelebner:roomdatabasebackup` Gradle dependency completely.
- Implement backup (export) and restore (import) of the notes database file directly via the Storage Access Framework (`ActivityResultContracts.CreateDocument` / `OpenDocument`), requiring zero storage/media runtime permissions.
- Keep the change working uniformly across the app's full supported range (`minSdk 21` through `targetSdk 36`) — SAF via `ActivityResultContracts` has worked this way since `androidx.activity` 1.1, well below `minSdk 21`'s ceiling.
- Preserve the existing `RoomBackupHandler` / `RoomBackupBuilder` / `BackupModel` domain seams so `BackupAndRestoreRepositoryImp`, `BackupAndRestoreNotesUseCase`, `MainViewModel`, and the drawer menu wiring in `MainActivity` need no behavioral changes beyond what's necessary to register the new SAF launchers.
- End state: the merged manifest contains no `READ_MEDIA_IMAGES`/`READ_MEDIA_AUDIO`/`READ_MEDIA_VIDEO`/`READ_EXTERNAL_STORAGE` entries at all (not suppressed via `tools:node="remove"` — genuinely absent, because nothing declares them).

**Non-Goals:**
- Encryption support (the app doesn't use the library's `backupIsEncrypted` option today; not being added).
- Multiple backup file management / `maxFileCount` pruning (the app uses `BACKUP_FILE_LOCATION_CUSTOM_DIALOG`, a single user-chosen file per operation, not the library's internal/external managed-directory modes with retention — nothing changes here).
- Any change to backup file *format* — it stays a raw copy of the Room SQLite file, so old backups made by the library remain restorable by the new code and vice versa.
- Solving the stale-`AppDatabase`-singleton-after-close problem more elegantly than "restart the app" — out of scope; that behavior is preserved as-is.

## Decisions

**Call `ActivityResultContracts.CreateDocument`/`OpenDocument` directly; drop the library rather than patch around its permission gate.**
The permission request is unconditional inside the library's `backup()`/`restore()` methods for `BACKUP_FILE_LOCATION_CUSTOM_DIALOG` — there's no builder flag to disable it, and no other backup-location mode fits this app's UX (internal/external modes manage their own directory + a "pick from list" dialog, which is a worse experience than "user picks any location"). Alternative considered: keep the library but switch to `BACKUP_FILE_LOCATION_CUSTOM_FILE` (which skips the permission gate but expects the app to already have a `File` handle, i.e. still expects direct filesystem access rather than a SAF `Uri`/`ContentResolver` stream, which is exactly the pre-scoped-storage pattern Android has been moving away from since API 29). Rejected — it would keep a dependency around for essentially nothing (a thin `copy(File, File)` helper) while still not being SAF-native. Removing the dependency entirely and calling the two `ActivityResultContracts` directly is less code than adapting around the library either way.

**Keep the existing `RoomBackupBuilder` (Activity-scoped) / `RoomBackupHandler` (Singleton) split; move SAF launcher registration into the Activity-scoped side.**
This mirrors exactly why the split exists today: `registerForActivityResult` must happen before the host reaches `STARTED`, so the two launchers (`CreateDocument`, `OpenDocument`) get registered inside the `@ActivityScoped` implementation (replacing `RoomBackupBuilderImp`), which casts its injected `@ActivityContext Context` to `ComponentActivity` — the same cast the library performs internally today, so no new requirement is introduced. That implementation bridges each launcher's async callback into a `suspendCancellableCoroutine`, preserving the current `suspend fun backupInLocalStorage/restoreInLocalStorage` shape so the `@Singleton`-scoped `RoomBackupHandler` implementation, `BackupAndRestoreRepositoryImp`, `BackupAndRestoreNotesUseCase`, and `MainViewModel` need zero changes. Alternative considered: move all backup/restore logic into `MainActivity` directly and change the ViewModel/UseCase/Repository signatures to accept Activity Result callbacks — rejected as a much larger, unnecessary blast radius for what's fundamentally an implementation-detail swap.

**File copy: close `AppDatabase`, stream bytes via `ContentResolver.openInputStream`/`openOutputStream`, keep app-restart-after-op as-is.**
Same sequence the library used (`roomDatabase.close()` then raw byte copy, relying on Room's WAL checkpoint-on-close to make the on-disk file consistent) — reimplemented as a plain `input.copyTo(output)` between `ContentResolver` streams and `context.getDatabasePath("task_database")`'s `FileInputStream`/`FileOutputStream`, run on `Dispatchers.IO`. `MainViewModel` already sets `needsRestartApp = true` after both operations today, which is what makes the stale closed-singleton `AppDatabase.instance` safe to leave behind — no new handling needed.

**MIME type stays `application/octet-stream` for both directions.**
Matches exactly what the library used (`CreateDocument("application/octet-stream")`, `OpenDocument()` filtered to `arrayOf("application/octet-stream")`), preserving compatibility with existing backup files on users' devices and avoiding any need to register a custom MIME type or file extension association.

**Backup filename stays `$dbName-<timestamp>.sqlite3`, generated at call time instead of pre-built into a `BackupModel`.**
The current `RoomBackupBuilderImp.prepareBackupInLocalStorage()` eagerly builds a full `RoomBackup` config (including `.maxFileCount(5)`, unused under `CUSTOM_DIALOG`) before the user has chosen backup or restore. Since the new implementation has no equivalent library object to configure ahead of time, `BackupModel` becomes a thin marker that just carries a reference to the Activity-scoped SAF handler; the actual `CreateDocument` filename argument is computed when `backupInLocalStorage()` is invoked. This keeps `MainActivity.onCreate`'s existing `backupModel = roomBackupBuilder.prepareBackupInLocalStorage()` call site and `BackupModel` interface untouched.

## Risks / Trade-offs

- **[Risk] Losing the library's WAL-checkpoint-then-copy ordering guarantee if the reimplementation reorders `close()` vs. the copy.** → Mitigation: keep `roomDatabase.close()` strictly before any read of the database file, exactly matching the decompiled library's `doBackup`/`doRestore` ordering; verify with a manual on-device backup→modify-notes→restore round trip.
- **[Risk] `registerForActivityResult` must be called during Activity initialization (before `STARTED`); if the Hilt-provided `@ActivityScoped` object is constructed lazily on first use instead of eagerly, registration throws `IllegalStateException`.** → Mitigation: keep the same eager-construction pattern the app already relies on (`MainActivity.onCreate` immediately calls `roomBackupBuilder.prepareBackupInLocalStorage()`, forcing the `@ActivityScoped` provider — and thus launcher registration — to run before `onCreate` returns); verify by exercising backup and restore manually after a fresh app launch.
- **[Risk] Manual QA is the only verification available.** → Per `CLAUDE.md`, there's no real instrumented test coverage in this project; this flow was already only manually verified with the old library. Mitigation: tasks.md includes explicit manual verification steps (backup, restore, restore of a pre-existing library-produced backup file, on both a device/emulator at API 21–32-equivalent behavior and one at API 33+) as the primary safety net, plus confirming the merged manifest via `./gradlew :app:processDebugMainManifest` shows no `READ_MEDIA_*`/`READ_EXTERNAL_STORAGE` entries.
- **[Trade-off] No more "list of existing backups" restore dialog.** The library's `CUSTOM_DIALOG` mode already didn't provide one either (that's only `BACKUP_FILE_LOCATION_INTERNAL`/`EXTERNAL`) — restore has always been "user picks a file via system picker" in this app, so this is not a behavior change, just calling out that it isn't being added.

## Migration Plan

1. Implement the SAF-based `RoomBackupBuilder`/`RoomBackupHandler` replacement in `data/database/backup/` alongside the existing library-backed code (or directly replacing it, given the low risk and lack of automated coverage either way — a single-module app with no feature flag infrastructure doesn't warrant a parallel-run).
2. Update `di/ActivityScopedModule.kt` and `di/DataSourceModule.kt` bindings to the new implementations; remove the `RoomBackupLib`/`RoomBackupBuilderImp` classes and the library import.
3. Remove the `de.raphaelebner:roomdatabasebackup` dependency (and its `room-guava`/`room-rxjava2` exclusions, now moot) from `app/build.gradle`.
4. Rebuild and inspect the merged manifest (`app/build/intermediates/merged_manifest/debug/processDebugMainManifest/AndroidManifest.xml`) to confirm the four permissions are gone.
5. Manually verify on-device: backup → restore round trip (including restoring a backup file previously produced by the old library, to confirm format compatibility), on both an API ≤32 and an API 33+ target if available.
6. No rollback complexity beyond reverting the commit — no data migration, no server-side state; worst case a broken build/restore path is caught by the manual verification in step 5 before merge.

## Open Questions

None outstanding — the replacement mechanism (SAF via `ActivityResultContracts`), the seam to preserve (`RoomBackupBuilder`/`RoomBackupHandler`), and the file-copy semantics are all fully determined by matching the existing (decompiled) library behavior.
